背景

日志的重要性不言而喻。对于排查生产环境问题至关重要。基于日志数据，也可进行复杂的数据分析，提供架构调整所需的数据支撑。

好的日志，其表现不外乎这几点（欢迎补充）：

  1. 日志能尽可能包含上下文；
  2. 并且可解析，供其他程序自动处理。也就是日志需要结构化（structured logging）。

想法是好的，但是在开发过程中，极大概率是因为嫌麻烦，导致以上标准无法得到完美实施。

ps：后端打印日志，跟前端代码中手动事件埋点很相似的。

我们需要通过代码架构设计及开发规范来解决这个问题。

Go 实践

request scoped logger

每个请求都有各自的上下文，比如请求来源于不同的用户、不同的行为。在请求生命周期中，在所经过的所有方法内重复写 log.Info(userid, actionid)是非常痛苦的工作。需要为每个请求创建一个 logger，由这个 logger 维护好上下文，开发打印日志不用重复记录上下文。

context

request scoped logger 怎么服务于不同方法中，只能通过参数传递。一个 logger，作为每个方法的入参数略显怪异。

context 是Go官方提供的传递 request scoped variables 的方案。建议 logger 附着于 context 传递，显得比较"Go sytle"些。

通过 context 传递的 Value 是没有类型的，需要我们手动进行类型转换，也比较麻烦。我们需要一个强类型的 context。

Context 不是强类型的，也不用重新定义 Context。

只能使用 context.log 打印。

// A Request represents an HTTP request received by a server
// or to be sent by a client.
//
// The field semantics differ slightly between client and server
// usage. In addition to the notes on the fields below, see the
// documentation for Request.Write and RoundTripper.
type Request struct {

	// ctx is either the client or server context. It should only
	// be modified via copying the whole Request using WithContext.
	// It is unexported to prevent people from using Context wrong
	// and mutating the contexts held by callers of the same request.
	ctx context.Context
}

context 包

  1. request scoped context – per request/ per processing-unit 信息
  2. 关注横切 cross-cutting
  3. 不需要全局变量
  4. Context 中存储一个 logger，一个 profiling object 等。通过传递context，而不是具体的logger。Tagging requests with request IDs 这一节就是典型的context里维护一个 request scoped logger 的方案。https://blog.gopheracademy.com/advent-2016/context-logging/
  5. context还带有Deadline，CancelFunc 等 API。不能cancel thread，但是能cancel goroutine?？TODO
  6. The nice thing about using context for this is that a single extra argument can cover a potentially unlimited number of cut-across development patterns.
  7. context.Background() is supposed to be used at what you consider to be the “top level” of your program. The ideal state is where the main creates a background context, maybe tags it with the program name or something and then passes it into every single worker and routine that it starts for their specialization. 以一个为基础，在这个backgroud里就塞入应用名称？？？http.Request.Context是继承的哪？
  8. context.TODO() If you’re calling a function which has had the context.Context parameter added, but the caller doesn’t have it passed down to it, you can use context.TODO().

when you’re talking about concerns like logging or profiling, it just seems a bit ugly to pollute your function arguments for business logic with a log object, a database transaction handle, a profiling object, and whatever else. It’s also tedious and costly to do all that refactoring as solutions to new concerns are introduced.

You need another plan for this. That plan is context.

Instead of passing around a bunch of random objects for these concerns all over your code base, you can pass around just one, and those libraries can get things out of them by themselves when they need them.

context 维护的是一个链表。withValue 就是新建一个链表节点。新的context 拥有老链表的所有内容，想象下链表就知道了。一直找到父节点里也没找到为止。

Each context object is also immutable, although the values in it don’t necessarily have to be. The way to update maps with immutable objects in functional languages like Erlang is to create a new one with the new key added, and this is something like what context.WithValue does. It’s actually a singly linked list, and each link only holds a single key. It looks it up, and if it doesn’t find it, it passes it to the parent.

context.Backgroud()就是一个root节点，后面延伸多条岔路的。所以互不影响，很不错的设计啊。

从context里取东西，因为存的是interface{}，需要断言取出原值。
