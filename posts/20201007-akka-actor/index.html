Akka, a set of open-source libraries for designing scalable, resilient systems that span processor cores and networks.

Akka allows you to focus on meeting business needs instead of writing low-level code to provide reliable behavior, fault tolerance, and high performance.

To be successful, distributed systems must cope in an environment where components crash without responding, messages get lost without a trace on the wire, and network latency fluctuates. 这也是 Akka 解决的问题。

几个问题：

  1. Go goroutine + channel vs. Akka message passing 有何本质区别么？解决的是一个问题么？goroutine 只是单机的概念。Akka 分布式+容错+并发。
  2. https://doc.akka.io/docs/akka/current/typed/guide/index.html
  3. Akka 异步消息怎么适应实时的 API 呢？

Akka的作者看来，单机内多线程的通信问题与多机多线程没什么两样，Akka是适应单机与多机的统一模型。

多线程，主线程分发任务，任务线程执行任务，主线程需要处理与任务线程之间的通信。

跨网络，主线程与其他机器的线程交互除了是经过网络的，跟单机多线程的处理没有两样。主线程与其他机器线程交互的方式，是投递消息。Akka 让单机多线程也这么做，同样是消息投递。

Akka 的出现是为了适应现代计算机架构与分布式系统。

Akka 提高生产力的方面在于：

  1. 不用 Low-level 的处理多线程并行 building block，比如原子操作、锁。
  2. 不用写底层的网络通信。
  3. 还提供了一个高可用的集群架构。

Why modern systems need a new programming model

这篇文章讲的是 Akka 出现的动机。https://doc.akka.io/docs/akka/current/typed/guide/actors-motivation.html

现代架构是多线程、多CPU的架构，传统的 OOP 编程模型并不适合。OOP 面向对象编程并不是解决并行计算的模型。这里介绍下 Actor model。

To highlight issues that the actor model addresses, this topic discusses the following mismatches between traditional programming assumptions and the reality of modern multi-threaded, multi-CPU architectures:

  • The challenge of encapsulation
  • The illusion of shared memory on modern computer architectures
  • The illusion of a call stack

OOP 封装的挑战 —— 并没有解决多线程并发修改对象内部状态的问题

封装并没有解决对象被多线程并发访问（修改）的竟态问题。这时候只能使用锁来解决。锁并不美好，限制了并发，也容易写出死锁的代码。

OOP 的编程模型，我们很少考虑多线程。比较单线程思维，都是从对象A方法调用对象B，这个角度去思考。而实际上，在多线程环境，是线程在驱动整个调用链。

In summary:

Objects can only guarantee encapsulation (protection of invariants) in the face of single-threaded access, multi-thread execution almost always leads to corrupted internal state. Every invariant can be violated by having two contending threads in the same code segment. While locks seem to be the natural remedy to uphold encapsulation with multiple threads, in practice they are inefficient and easily lead to deadlocks in any application of real-world scale. Locks work locally, attempts to make them distributed exist, but offer limited potential for scaling out.

共享内存的错觉，在多线程、多CPU的架构下思考 —— CPU 写入一个变量，会先写入缓存，而不是直接进入共享内存

Programming models of the 80’-90’s conceptualize that writing to a variable means writing to a memory location directly.

On modern architectures - if we simplify things a bit - CPUs are writing to cache lines instead of writing to memory directly.

Most of these caches are local to the CPU core, that is, writes by one core are not visible by another. In order to make local changes visible to another core, and hence to another thread, the cache line needs to be shipped to the other core’s cache.

以前的编程模型假设，写入一个变量，是直接写入内存。实际上，并不是，是先写入缓存，而不是直接内存。然后就有了变量的可见性问题。在 Java 里，需要在变量前定义一些关键字来解决。

On the JVM, we have to explicitly denote memory locations to be shared across threads by using volatile markers or Atomic wrappers. Otherwise, we can access them only in a locked section. Why don’t we just mark all variables as volatile? Because shipping cache lines across cores is a very costly operation! Doing so would implicitly stall the cores involved from doing additional work, and result in bottlenecks on the cache coherence protocol (the protocol CPUs use to transfer cache lines between main memory and other CPUs). The result is magnitudes of slowdown.

为什么不为每个变量声明为volatile，这样所有线程都可见呢。因为这样会要求CPU把当前core的cache移动到其他core的cache，这是耗时操作！

所以，akka的思路是，干脆不考虑共享，直接通过消息投递。线程负责好这个对象，在akka里，是actor吧。

In summary:

There is no real shared memory anymore, CPU cores pass chunks of data (cache lines) explicitly to each other just as computers on a network do. Inter-CPU communication and network communication have more in common than many realize. Passing messages is the norm now be it across CPUs or networked computers. Instead of hiding the message passing aspect through variables marked as shared or using atomic data structures, a more disciplined and principled approach is to keep state local to a concurrent entity and propagate data or events between concurrent entities explicitly via messages.

摩尔定律失效了，单核上的提升比较有限了。现代 CPU 的发展，是通过多核的方式提高性能的。所以 CPU core 之间的通信，与 CPU 网络间的通信是可以类比的。

调用堆栈上的错觉 —— 这是单线程内的处理逻辑，无法使用多线程场景

Call stacks do not cross threads and hence, do not model asynchronous call chains.

调用堆栈，一般的印象是在单个线程内的方法调用堆栈，throw exception 也是在单线程内的。调用堆栈也可以是跨线程、跨网络的，这是Akka提醒我们的？

为了提高运行效率，势必会有把一些计算任务委托给工作线程的工作。这时候该如何思考调用堆栈。

会出现如下的现象，工作线程出现 exception 后，工作状态也丢了。怎么跟主线程汇报呢？no way了，除非写try catch 代码吧。这跟网络间交互，网络问题导致工作线程无法汇报给另一台机器的主线程是一样的。

unexpected phenomena: the actual task, that the thread was currently working on, is no longer in the shared memory location where tasks are taken from (usually a queue). In fact, due to the exception reaching to the top, unwinding all of the call stack, the task state is fully lost!

基于 Call stack 的错误处理在 task-delegating、分布式计算的场景已经不适宜了。需要引入显式的错误信号机制。

In summary:

To achieve any meaningful concurrency and performance on current systems, threads must delegate tasks among each other in an efficient way without blocking. With this style of task-delegating concurrency (and even more so with networked/distributed computing) call stack-based error handling breaks down and new, explicit error signaling mechanisms need to be introduced. Failures become part of the domain model.

Concurrent systems with work delegation need to handle service faults and have principled means to recover from them. Clients of such services need to be aware that tasks/messages might get lost during restarts. Even if loss does not happen, a response might be delayed arbitrarily due to previously enqueued tasks (a long queue), delays caused by garbage collection, etc. In face of these, concurrent systems should handle response deadlines in the form of timeouts, just like networked/distributed systems.

How the Actor Model Meets the Needs of Modern, Distributed Systems

https://doc.akka.io/docs/akka/current/typed/guide/actors-intro.html

Usage of message passing avoids locking and blocking

An important difference between passing messages and calling methods is that messages have no return value. By sending a message, an actor delegates work to another actor. As we saw in The illusion of a call stack, if it expected a return value, the sending actor would either need to block or to execute the other actor’s work on the same thread. Instead, the receiving actor delivers the results in a reply message.

Object -> Actor，invoke method -> message passing。Actors react to messages just like objects “react” to methods invoked on them., they react to incoming messages sequentially, one at a time. 因为 Actor 同时只处理一条 message，所以没有并发问题，被顺序处理解决了。调用没有阻塞了，保证两个actor可以并行运行。也就是说，看似单个actor是顺序修改内部状态的，没有并行，但是多个actor是并行的。

保持了封装性的同时，不再需要锁和原子包装来解决并发修改内部状态的问题。

To accomplish this behavior, actors have:

  • A mailbox (the queue where messages end up).
  • A behavior (the state of the actor, internal variables etc.).
  • Messages (pieces of data representing a signal, similar to method calls and their parameters).
  • An execution environment (the machinery that takes actors that have messages to react to and invokes their message handling code). An execution environment orchestrates a pool of threads to drive all these actions completely transparently. 复杂逻辑是这块在处理啊。
  • An address (more on this later).

This is a very simple model and it solves the issues enumerated previously:

  • Encapsulation is preserved by decoupling execution from signaling (method calls transfer execution, message passing does not). 保留了封装性。
  • There is no need for locks. Modifying the internal state of an actor is only possible via messages, which are processed one at a time eliminating races when trying to keep invariants. 顺序执行，不需要锁。
  • There are no locks used anywhere, and senders are not blocked. Millions of actors can be efficiently scheduled on a dozen of threads reaching the full potential of modern CPUs. Task delegation is the natural mode of operation for actors. 无锁，sender 不会阻塞。无数的 actor 会被高效地调度在一堆线程上，充分利用 CPU 资源。
  • State of actors is local and not shared, changes and data is propagated via messages, which maps to how modern memory hierarchy actually works. In many cases, this means transferring over only the cache lines that contain the data in the message while keeping local state and data cached at the original core. The same model maps exactly to remote communication where the state is kept in the RAM of machines and changes/data is propagated over the network as packets. actor 的状态是本地的，不必共享！符合现代内存架构（CPU缓存+内存的架构）

Actors handle error situations gracefully

第一种error是task本身的error，这个在业务范畴里。第二种比较重要，是actor本身遇到错误。这里actor是树状层级的，都有一个parent，actor出错了，由其parent来决定如何处理这个失败。

  • The second case is when a service itself encounters an internal fault. Akka enforces that all actors are organized into a tree-like hierarchy, i.e. an actor that creates another actor becomes the parent of that new actor. This is very similar how operating systems organize processes into a tree. Just like with processes, when an actor fails, its parent actor can decide how to react to the failure. Also, if the parent actor is stopped, all of its children are recursively stopped, too. This service is called supervision and it is central to Akka.

Akka provides the following behavior for message sends:

  • At-most-once delivery, that is, no guaranteed delivery. 最多一次传递。sender 发完就忘了，性能最高。至少一次传递，需要receiver的ACK，需要重试。正好一次传递，it requires the state to be kept at the receiving end in order to filter out duplicate deliveries
  • Message ordering is maintained per sender, receiver pair.

不能保证准确的正好一次发送，会不会出现很多问题啊！！！这么多原因，看的云里雾里。不管怎么样，需要应用层处理消息的准确传递了。Message里加上 RequestID。

For these reasons Akka lifts the responsibilities of guarantees to the application itself, i.e. you have to implement them yourself with the tools that Akka provides. This gives you full control of the guarantees that you want to provide.
