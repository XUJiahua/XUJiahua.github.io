Kubernetes 的知识点太多了，网上资料够多，重头梳理一遍，没有意义。用问答的方式，理解下 Kubernetes。

Docker 的优点

运行 Java、Python 应用，需要运行所在的主机安装 Java、Python 的运行环境，多个应用共用一套运行环境难免会有依赖冲突。Docker 能做到依赖与应用使用容器技术包装在一起，宿主机只要有Docker运行环境即可让多版本的Java程序在一台主机上运行。

比起 Virtual Machine，是一个很经济的方案。做到隔离，消耗更小。

Container 就是应用的抽象。把细节，比如环境依赖，用容器思想docker包装起来。

我们只关注网络。。部署时候关注资源、MEM、CPU。

Docker 的缺点（Kubernetes 的意义）

只能完成单机中多 Container 网络的通信。因为共用一个网关 docker0。

Linux （学习 Docker 强烈建议在 Linux 下学）下启动一个容器。

docker run nginx

在另一个终端下，先查看容器的IP。在宿主机可以直接访问容器IP。

docker inspect zen_haibt | grep IPAddress
            "SecondaryIPAddresses": null,
            "IPAddress": "172.17.0.2",
                    "IPAddress": "172.17.0.2",

curl 172.17.0.2

Docker 本身无法做到的事情：

  1. 容器在多机环境下通信。
  2. 自动的容器编排，哪台宿主机有空闲资源可用，部署这个容器。
  3. 应该也是容器编排问题了，端口冲突问题。因为容器最终得到流量，是通过与宿主机网络做绑定，宿主机网络的端口号是共享的。

关于容器如何编排，多机下容器网络怎么通信，这是 Kubernetes 解决的问题。

Kubernetes 的好处

Kubernetes 集群创建了一个内部网络。Deployment/Service都是基于这个内部网络的逻辑抽象。

没有应用端口冲突：每个Pod相当于一个小主机，有自己的CPU、内存（spec里指定）、网络栈（集群分配了一个ClusterIP）。因为Pod里只有自己的应用，不会与其他应用争端口。

自动伸缩方便。声明式定义deployment副本数，集群自动执行。减少 Provision 机器，部署、负载均衡等操作。集群资源不够，加主机就行。

微服务治理：Pod 内加入sidecar容器，流量分流也能做了。

Kubernetes 的架构

使用主流的Master/Worker的架构。

Master是Kubernetes Control Plane，Worker是 Kubernetes Node。

  1. kubectl 是与 kube-api-server 通信。
  2. 使用 yaml 文件描述资源（Deployment，Service等都是资源）定义。
  3. kubectl apply 提交资源文件。

参考：

  1. Kubernetes Components https://kubernetes.io/docs/concepts/overview/components/

Kubernetes 的生产环境搭建

生产集群可以考虑使用部署工具创建，也可以直接使用云服务。

官方文档提到的部署工具：

  1. kubeadm
  2. kops
  3. Kubespray

其他安装方式：

  1. OpenShift 面向开发者多一些？
  2. Rancher 面向运维多云集群管理

使用云服务，可以直接跳过 Master 节点的安装，只需要准备几台 ECS 作为 Worker 节点加入到集群。

好处是，托管了集群的运维工作。

  1. Client certificates renewals
  2. 集群的监控

Kubernetes 的本地开发环境搭建，一般使用 minikube，介绍下 minikube

当我们说到生产环境，一般都是指的 Linux 环境。Docker 等容器方案是 Linux 上的产物。为了方便 Dev 在本地（Windows/MacOS）创建一个 Kubernetes 集群，便有了 minikube。使用 minikube 创建多节点集群仍然是实验性的。

使用 libmachine 创建 Linux VM。libmachine 是 Docker Machine 的核心库，支持各种 VM Driver（比如 VirtualBox、Hyper-V）。

使用 kubeadm 在 VM 上创建集群。

Minikube uses libmachine for provisioning VMs, and kubeadm to provision a Kubernetes cluster.

For more information about Minikube, see the proposal.

参考：

  1. Minikube Design https://kubernetes.io/docs/setup/learning-environment/minikube/#design
  2. Minikube Documentation https://minikube.sigs.k8s.io/docs/

Kubernetes Cluster 有一个内部网络（a flat, cluster wide, address space），每个Pod都有一个IP，ClusterIP 是内部 IP。

外部网络（宿主机网络）与内部网络怎么交互。这是 Service 的作用。

NodePort，生产环境不实用。

Service 的作用

Container/Pod都是容易挂的东西，不持久。这时候引入 Service，解决了单一入口和负载均衡的问题。把后面的细节屏蔽掉了。这就是抽象，不用管我里面是什么，你只要关注我暴露出的service，这个接口即可。

ClusterIP 集群内 IP。可以创建一个curl Pod，在里面试验连通性。

NodePort targetPort: is the port the container accepts traffic on, port: is the abstracted Service port nodePort: 30000~xxxxx之间的端口号，可随机可指定。

GitOps：基于 Kubernetes 的运维调整

  1. 应用容器化，提交到镜像仓库。开发的交付产物是镜像。
  2. 应用与配置分离。
  3. 测试环境的搭建，也可以使用资源定义文件 yaml 管理。
  4. 准备yaml资源定义文件，并使用 git 进行版本管理（Configuration files should be stored in version control before being pushed to the cluster. This allows you to quickly roll back a configuration change if necessary. It also aids cluster re-creation and restoration.）。
  5. kubectl apply 提交 yaml 文件，集群按照定义执行部署逻辑。
  6. 部署失败，可以使用git回退到前一版本，再次提交部署。
  7. Dashboard 上可以 autoscaling。

其他需要准备的：

  1. 镜像服务。
  2. 日志收集中心。虽然也可以通过 dashboard或是kubectl查看单台的。
  3. helm？helm 能用git管理起来么？不同的团队用不同的namespace吧。
