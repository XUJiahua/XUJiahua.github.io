目前存在的问题：

  1. 持续集成 + 持续部署，也就是CI/CD目前是一条 pipeline。因为两周生命周期是不一样的，建议分开。—— GitLab CI 支持并行的 pipeline，就不会有这方面的问题了。
  2. 准确的说，除了应用打包，持续集成基本为 0。没有单元测试、code lint 静态检查、没有集成测试。
  3. CD 流程，应该由测试人员选择使用哪个版本进测试环境，而不是自动部署到测试环境。持续部署，就是部署到生产环境。假设经过了CI以及测试。

背景知识

测试简介

测试金字塔。越往下，越独立、测试快速，越往下，越集成、测试慢速。

按照测试类型和方式来对各种测试分组。

以上两图来源：https://medium.com/@lawrey/unit-tests-ui-tests-integration-tests-end-to-end-tests-c0d98e0218a6

单元测试在本地用mock跑测试。

集成测试在本地用真实依赖跑测试，比如数据库。

E2E测试，需要交互，真实。

CI/CD

CI is usually implemented with pipelines that run periodically or are triggered when a developer pushes a code change. For example, a CI pipeline could have three jobs: one that runs a linter, one that runs unit tests, and one that builds an artifact from the source code.

The usual output of a CI pipeline is an artifact in an artifact storage system.

CI/CD的生命周期其实不同。

Many organizations create a single pipeline that implements both CI and CD. We do not recommend this setup because CI and CD have the following conflicting goals:

  • The goal of CI is to provide a short feedback loop to developers. A CI pipeline should run in less than 10 minutes.
  • The goal of CD is to ensure the stability of your production environment. This goal might necessitate processes that can last several hours (such as canary analysis).

When you’re actively developing an application, with several commits to the main branch each day, it’s not ideal to trigger your full CD pipeline after your CI pipeline succeeds if your CD pipeline requires several hours.

SourceURL: https://cloud.google.com/solutions/addressing-continuous-delivery-challenges-in-a-kubernetes-world

CI 工作 —— 提高代码质量

  1. golang 单元测试及覆盖率结果输出。
  2. golang 静态检查及检查结果输出。
  3. 静态检查工具开发？比如 panic 风险检查。
  4. 集成测试和性能测试尽量复用脚本，首选使用 Python，集成测试已经使用 pytest 了，性能测试框架可以使用 Locust。
  5. 使用 docker-compose 创建本地集成测试环境，运行集成测试脚本。
  6. Build image，并上传到镜像仓库。
  7. 与 gitlab CI 集成。
